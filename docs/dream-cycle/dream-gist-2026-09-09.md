# Swarm SOTA Report — 2026-09-09

TL;DR: Tonight's `swarm` deep-dive found that `AgentPool.performHealthChecks()` (`v3/@claude-flow/swarm/src/agent-pool.ts`) has been silently unable to ever detect a dead/hung agent, in every agent pool the coordinator creates, since the method was written: its "still healthy" branch stamped `pooled.agent.lastHeartbeat = now` on every tick, and `updateAgentHeartbeat()` — the only other legitimate way to advance that field — has zero call sites anywhere in the `v3/` tree. The health check's own tick was therefore the sole thing keeping every pooled agent's heartbeat "fresh," so `timeSinceLastActivity` could never exceed one health-check interval, the `healthCheckIntervalMs * 3` unhealthy threshold could never be crossed, and `replaceUnhealthyAgent()` could never fire — for any agent, in any pool, ever — regardless of whether the agent was actually still alive. Fixed by removing the self-stamping side effect, matching the correct pattern already implemented next to it in the same package (`UnifiedCoordinator.checkHeartbeats()`, which never touches `lastHeartbeat` on its "still fine" branch). Five research roles ran in parallel tonight; the deep-researcher/competitor-analyst role's top pick (a gossip-consensus per-key-versioning correctness bug) and three other candidates are documented below as strong candidates for future nights, not folded into tonight's patch, per repo convention (one conceptual change per PR) and the current PR backlog.

## Ruflo Current Capability

`AgentPool` (`v3/@claude-flow/swarm/src/agent-pool.ts`) is wired live into `UnifiedCoordinator.initializeAgentPools()` (`unified-coordinator.ts:624-660`), which creates one pool per `AgentType` and one per `AgentDomain`, both during `initialize()` — this is not orphaned code, every coordinator instance runs it. `performHealthChecks()` (line 368, invoked every `healthCheckIntervalMs` via `startHealthChecks()`'s `setInterval`) is the pool's only dead-agent detector: it checks `timeSinceLastActivity = now - pooled.agent.lastHeartbeat` against `unhealthyThresholdMs = healthCheckIntervalMs * 3`, decrementing health and eventually calling `replaceUnhealthyAgent()` if an agent goes silent. Before tonight's fix, the "still healthy" branch also executed `pooled.agent.lastHeartbeat = now`, and grepping the entire `v3/` tree for `.updateAgentHeartbeat(` calls (the only other public API that legitimately advances this field) returns zero hits — so this self-stamping was the *only* thing touching `lastHeartbeat` after agent creation, for every agent pool in the system. The sibling implementation in the same package, `UnifiedCoordinator.checkHeartbeats()` (line 956), gets this right: it only advances `lastHeartbeat` from `handleHeartbeat()` (a genuine external event) or `recoverAgent()` (an explicit reset after recovery), never merely from "the check ran and found things fine."

## Hypothesis

> Given an `AgentPool`-managed agent that has stopped reporting real liveness (in production, every agent, since `updateAgentHeartbeat()` has zero callers), when `performHealthChecks()`'s "still healthy" branch is changed to no longer stamp `lastHeartbeat = now` as a side effect of merely running the check, then an agent silent for longer than `healthCheckIntervalMs * 3` should be correctly flagged unhealthy (`status: 'error'`, health decremented) and, once health reaches 0, replaced via `replaceUnhealthyAgent()` — relative to today's baseline where this never happens regardless of how long an agent has been silent — subject to: (1) an agent receiving genuine `updateAgentHeartbeat()` calls within the grace window continues to be treated as healthy (no regression for legitimately-alive agents); (2) the health `+0.1` recovery increment for agents within the grace window is preserved; (3) zero added latency, $0 cost, fully deterministic test coverage; (4) the full existing test suite remains green.

Frozen before evaluation; not modified after seeing results.

## Security Review

Not primarily security-sensitive, but directly reliability-relevant: before this fix, a hung/crashed agent in any pool would be silently retained forever by the pool's own bookkeeping (never marked `'error'`, never replaced), meaning tasks could keep being routed to (or the pool could keep reporting healthy capacity around) an agent that has actually stopped functioning — an availability/correctness gap, not a new attack-surface, credential-exposure, or authority-boundary change. ## Additional candidates surfaced but not selected tonight (STEP 3.2)

Scored under `0.25·Ruflo_fit + 0.20·testability + 0.20·measurability + 0.15·production_value + 0.10·novelty + 0.10·reviewability` (1-5 each); tonight's architecture-reviewer finding (AgentPool heartbeat self-reset) scored a maximum 5.0/5.0 (5 on every dimension — universal blast radius across every pool, a clean 1-line fix, and a pre-existing correct sibling implementation in the same package to pattern-match against) and was selected over the deep-researcher's top external-literature pick:

1. **Gossip consensus per-key-versioned merge** (score 4.65, `consensus/gossip.ts` `handleStateMessage`/`antiEntropy`) — a single scalar `node.version` gates overwriting the *entire* state map, so an unrelated key update from a peer can clobber a locally-newer key; three independent 2026 papers (Token Coherence, StateFuse, CoAgent) converge on "ship deltas with fine-grained ordering, not whole-state." Real correctness bug, deterministic test plan ready — strong pick for a future swarm night, contingent on how much production traffic actually uses gossip- vs. raft-mode consensus (CLAUDE.md's documented default is raft).
2. **Byzantine confidence-weighted vote tally** (score 4.55, `consensus/byzantine.ts` `vote()`) — `ConsensusVote.confidence` (types.ts:222) is declared and populatable but never read in `vote()`'s binary tally; CP-WBFT/SAC (2025-26) show confidence-weighting beats binary majority under Byzantine LLM agents. Flagged risk: superficially resembles the already-fixed `weightedConsensus()` trust-weight bug (different file, different mechanism — static trust vs. per-vote confidence) — a reviewer could reasonably ask "didn't we just do this."
3. **Broadcast-path retry/failure blackhole** (score 4.55, `message-bus.ts` `handleDeliveryError`) — the repo's own code comment (added by the 2026-08-19 merged fix) already discloses that broadcast retries re-queue under a `'broadcast'`-keyed queue nobody drains, silently losing a failing broadcast subscriber's retries/failure event. Lowest novelty (self-disclosed, not newly discovered) but narrowest, safest scope.
4. **AgentPool.acquire() load/health-aware selection** (score 3.75) — picks from `available` via bare `Set` iteration order, ignoring `usageCount`/`health`/`workload`; Kairos/SwarmX (2025-26) show workload-aware dispatch cuts latency 17.8-28.4% in shared-serving settings (lower direct transfer to Ruflo's local-process pool).
5. **Phi-accrual adaptive heartbeat detector** (score 3.55, `unified-coordinator.ts` `checkHeartbeats()`) — replaces the textbook-naive fixed `3x interval` cutoff with a jitter-aware suspicion score (Hayashibara 2004, used in Cassandra/Akka/Hazelcast); weakest "genuinely new" claim of the five (foundational, not a 2026 paper) but a real robustness improvement, and complementary to tonight's fix (tonight fixes *whether* the detector can fire at all; this would fix *how well-tuned* its threshold is).

Also noted, lower priority: `TaskOrchestrator.getTaskMetrics()`'s `totalQueueTime` is declared and included in `averageQueueTime`'s denominator but never incremented anywhere (`coordination/task-orchestrator.ts`) — always reports 0; and `getQueuePosition()`'s local `priorityOrder` map uses `'normal'` where the real `TaskPriority` type (and the correct maps in `getNextTask()`/`getPriorityQueue()` in the same file) use `'medium'` — the task-queued telemetry event silently mis-ranks the *default* priority. Both are real but lower production value (metrics/telemetry only, not behavior-affecting) than tonight's pick.
