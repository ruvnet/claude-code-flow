# Memory SOTA Report — 2026-09-08

TL;DR: Tonight's memory deep-dive confirmed and closed a gap flagged (but not selected) by last night's memory-scan finding: `MemoryConsolidator.dedup()` (`v3/@claude-flow/memory/src/consolidator.ts`) only ever collapsed duplicates via byte-exact SHA-256 content hashing, even though every stored entry already carries a computed `.embedding` and the method already holds a handle to the adapter's incrementally-synced `HNSWIndex` — used only for point-removal bookkeeping, never queried for similarity. This is the same "signal already computed, live path discards it for a worse proxy" bug class as three recently-fixed/merged findings (2026-09-03 MMR/#3169, 2026-08-25 PQ-dispatch/#3094, 2026-08-28 HybridBackend-weights/#3119). Five parallel research roles converged independently on the same candidate and patch shape. An orphaned second implementation, `MemoryDomainService.consolidate()` (~700 LOC, zero tests, unreachable from the package's public exports), already does real embedding-cosine grouping but was confirmed NOT directly reusable (it's bound to an injected `IMemoryRepository` requiring a real per-entry `searchByVector()` round-trip; the in-scope `HNSWIndex` handle is strictly cheaper). Fixed by adding an embedding near-duplicate pass directly in `consolidator.ts`, reusing the already-loaded embedding and index with zero extra backend round-trips. An independent adversarial critic then found and this session fixed a real, bounded convergence bug in the first cut of the patch (duplicate clusters wider than the 8-entry search window split into multiple survivors within one call) — documented in full below, including the reproduction and the fix.

## Ruflo Current Capability

`MemoryConsolidator.dedup()` (`v3/@claude-flow/memory/src/consolidator.ts:140-210` pre-fix) buckets every entry by `sha256(content)` and merges byte-exact matches only — structurally blind to paraphrases/reformattings. It's invoked via `runAll()` (sweep → dedup → compact), reached by `UnifiedMemoryService`'s background timer (opt-in, `config.consolidator.autoRun`) and by the AgentDB `nightlyLearner` controller.

At the call site, `entries: Map<string, MemoryEntry>` is already fully resident with each entry's `.embedding?: Float32Array` (`types.ts:66`) inline, and `index: HNSWIndex` is already an in-scope, incrementally-synced handle exposing `.search(query, k, ef?)` — confirmed via direct read of `agentdb-adapter.ts` (index kept in sync on every write/delete) and `hnsw-index.ts` (`search()` is pure in-process graph traversal, no I/O). Fetching a similarity signal here costs zero extra backend round-trips.

Ruflo also ships a second, orphaned consolidation implementation: `MemoryDomainService.consolidate()` (`domain/services/memory-domain-service.ts:135-331`) does real embedding-cosine grouping (thresholds 0.95 dedupe / 0.8 merge) via `repository.searchByVector()` — but `repository: IMemoryRepository` is an injected interface requiring a genuine async round-trip *per entry* for a real backend, and the concrete backing repository (`HybridMemoryRepository`) does its own brute-force O(n) linear scan, not even HNSW-backed. The whole domain+application DDD chain dead-ends at its own barrel exports — confirmed via repo-wide import grep — and is explicitly excluded from the package's public surface (`index.test.ts:43` asserts `HybridMemoryRepository` must not be exported), consistent with a deliberate ADR-125-style quarantine rather than pure oversight. Zero test files exist for any file in this chain. **Conclusion, independently reached by two research roles**: wiring in the full domain-service architecture is not the smallest fix and was not selected; the in-scope `HNSWIndex` + already-resident `.embedding` is a strictly cheaper, more direct fix.

One more live gap surfaced while verifying the above (not previously documented): `dedup()`'s per-entry removal loop deletes IDs from `namespaceIndex`/`tagIndex` but — unlike `sweepExpired()`, which explicitly prunes now-empty `Set`s — never removes an emptied `Set` from its parent `Map`, so these maps grow unboundedly across many dedup cycles in a long-lived process. Not fixed tonight (separate, smaller, lower-value finding — see Additional Candidates below).

Ruflo's hash-exact-only baseline sat below every framework-layer competitor here and at parity with the vector-DB layer's default of doing nothing. Tonight's fix — an explicit, documented, conservative cosine threshold (0.95) feeding the existing keeper-selection logic — moves Ruflo onto the same mechanism class as CrewAI's 0.85 gate, the most reproducible and simplest-to-benchmark option in this table (versus Mem0/Zep/LangMem's non-deterministic LLM-mediated judging, or Graphiti's much heavier graph-structural machinery). It does not reach Mem0/Zep's *contradiction resolution* (rewriting superseded content, not just dropping a near-duplicate) — a legitimate next rung, out of scope tonight.

## Hypothesis

> Given `MemoryConsolidator.dedup()` operating on entries that already carry a resident `.embedding: Float32Array` and an already-populated, incrementally-synced `HNSWIndex` handle it holds but never queries for similarity, when a near-duplicate detection pass is added that queries `index.search()` for each hash-pass-surviving entry with an embedding and merges any group whose cosine similarity is at or above a configurable `similarityThreshold` (default 0.95, matching the orphaned domain-service's own constant) using the existing keeper-selection strategies, then `dedup()` should catch semantic near-duplicates (paraphrases/reformattings) that byte-exact SHA-256 hashing structurally cannot, relative to baseline (hash-exact-only, near-duplicates never merged), subject to: (1) all pre-existing hash-exact-dedup tests and behavior remain unchanged; (2) the near-dup pass is strictly additive — no survivor is dropped without an above-threshold match, and hash-exact duplicates are still merged even without embeddings; (3) entries without `.embedding`, or an index configured with a non-cosine metric, fall back to exactly today's hash-only behavior; (4) a single `dedup()` call fully converges a duplicate cluster of any size to one survivor, not just clusters within the search-neighborhood width; (5) $0 evaluation cost, fully deterministic test-only evaluation, zero LLM calls.

Frozen before evaluation began. Condition (4) was added mid-session after the adversarial critic (STEP 10) reproduced a violation of it in the first cut of the implementation — see Evaluation below for why this is a legitimate hypothesis refinement (a genuinely new, previously-unstated condition the critique surfaced) rather than a post-hoc loosening: the fix was applied to satisfy the *stronger* condition, not to relax the hypothesis to match a weaker result.

## Security Review

Not the primary focus, but directly relevant to data-retention correctness: this pass *deletes* entries judged near-duplicate, so an adversary who could influence embedding generation to force a coincidental high-cosine collision with a legitimate memory could, in principle, cause that memory to be silently dropped during consolidation. Mitigations already in place: the default threshold (0.95) is conservative and requires near-exact vector alignment, not merely "related" content; the pass only runs during consolidation (background timer or `nightlyLearner`), not on the synchronous write/store path, so it isn't reachable from a single malicious write in real time; and it operates purely on already-trusted, already-embedded internal state — no new network, filesystem, or credential surface is introduced (confirmed line-by-line by the adversarial critic). No fix required tonight; flagging the threshold-as-attack-surface framing for future `security`-DEEP consideration if Ruflo's embedding-generation path itself is ever exposed to less-trusted input.
