# Performance SOTA Report — 2026-09-10

TL;DR: Tonight's performance deep-dive found a genuine algorithmic-efficiency regression in `mmrRerank()` (`v3/@claude-flow/memory/src/smart-retrieval.ts`), the MMR diversity-reranking step behind `smartSearch`/`applyMMR` — the retrieval entry point on Ruflo's memory/ReasoningBank hot path. The function eagerly re-tokenized every remaining candidate's content string on *every* outer-loop pass (O(N × limit) `tokenize()` calls), a pattern that predates and survived PR #3169 (merged 2026-09-05) unchanged. #3169 wired embedding-cosine similarity through as the *preferred* comparison path whenever both compared candidates carry well-formed, matching-dimension embeddings — which is now the common production case, since Ruflo's own retrieval pipeline populates `.embedding` upstream. That means the eager tokenization this fix replaces was, in the common case, pure wasted work: computed and then thrown away by `pairSimilarity()`'s cosine branch almost every time. Fixed by making tokenization lazy and cached per-candidate via a `Map<SearchCandidate, Set<string>>`, so tokens are computed at most once per candidate and only when the token-Jaccard fallback path is actually exercised. Measured: `tokenize()` call count drops from 400 to 0 on a 30-candidate/limit-20 all-embedded corpus (stash-isolated: fails against real baseline, passes against candidate), and a `vitest bench` wall-clock comparison shows the candidate **5.88x faster** (mean 0.1148ms vs. 0.6745ms) on the same corpus shape. Five research roles ran in parallel tonight; a live, reachable hive-mind consensus-strategy bug (init-time `byzantine`/`gossip`/`crdt` selection is silently discarded — every proposal resolves via plain Raft majority regardless) is documented below as a candidate for a future `hive-mind`/`swarm` night rather than folded into tonight's single-conceptual-change patch.

## Ruflo Current Capability

`smartSearch()` (`v3/@claude-flow/memory/src/smart-retrieval.ts:442-531`) is Ruflo's LongMemEval-derived retrieval pipeline (ADR-090): query expansion → multi-query RRF fusion → recency boost → MMR diversity reranking → session round-robin. Phase 4 (`mmrRerank`, lines 279-343 pre-fix) greedily selects candidates by `λ·relevance - (1-λ)·max_similarity_to_selected`, where similarity is embedding-cosine when available (PR #3169, 2026-09-03/05) or token-Jaccard otherwise (`pairSimilarity`, lines 324-338). The bug: `candTokens = tokenize(cand.candidate.content)` (former line 299) ran inside the O(remaining.length) inner loop on *every* outer pass, and `selectedTokens.push(tokenize(...))` (former lines 290, 316) ran eagerly for every selected candidate too — regardless of whether the embedding-cosine branch was about to make those tokens irrelevant. A default `smartSearch()` call (`fanOutK = limit×3`, MMR `limit = min(limit×2, scored.length)`) feeds `mmrRerank` up to 30 candidates with an internal limit of 20 — 19 outer passes × up to 29 remaining candidates ≈ 551 theoretical max tokenizations (400 measured on this corpus), versus 0 needed once embeddings are populated. `smartSearch` is invoked on every ReasoningBank/agent-memory query, so this cost compounds silently on a path the project explicitly optimizes elsewhere (HNSW, RaBitQ, Int8 quantization) — undercutting those gains downstream in the same pipeline.

## Hypothesis

> Given `mmrRerank()` invoked on a candidate set where both compared candidates in a pairwise MMR comparison carry well-formed, matching-dimension embeddings (the common case since PR #3169), when tokenization is made lazy and cached per-candidate instead of eager per-outer-pass, then `tokenize()` call count and wall-clock time for `mmrRerank` should decrease materially relative to the pre-fix baseline, subject to: (1) selection output (ranked order and scores) is byte-for-byte identical to the pre-fix baseline across all-embedded, no-embedding, and mixed candidate sets — this is a pure efficiency refactor, not a behavior change; (2) the existing `smart-retrieval`/`mmr-benchmark` test suites remain green; (3) zero added LLM/API cost; (4) no latency regression in the token-Jaccard fallback path (missing/malformed/mismatched embeddings).

Frozen before evaluation began; not modified after seeing results.

## Scan Findings: hive-mind

**New, code-verified finding — the consensus strategy selected at `hive-mind init` is silently discarded; every proposal resolves via plain Raft majority regardless of configuration.** The reachable implementation behind both the `claude-flow hive-mind` CLI and its MCP tool is a self-contained JSON-state simulator (`v3/@claude-flow/cli/src/mcp-tools/hive-mind-tools.ts`) that never imports `@claude-flow/swarm`'s real `ConsensusEngine`/`ByzantineConsensus`/`RaftConsensus`/`GossipConsensus` implementations at all — those exist and are genuine (~15-17KB each) but are architecturally dead code from the CLI's perspective, consistent with the recurring "exists but nothing calls it" pattern (cf. PR #3243). Inside the reachable simulator: `hive-mind_init` (line 22, 310, 326) stores a 5-way `consensusStrategy` (`raft|byzantine|gossip|crdt|quorum`) on `state.consensusStrategy`. `hive-mind_consensus` — the tool that actually creates and votes on proposals — uses a *different, narrower* type (`'bft' | 'raft' | 'quorum'`, line 43) read from a **per-call** `strategy` input param defaulting to `'raft'` (line 551), and never reads `state.consensusStrategy` anywhere (grep-confirmed: the field is written once, echoed in status output twice, never consumed by `calculateRequiredVotes`/`tryResolveProposal`). The CLI's own `consensus` subcommand (`v3/@claude-flow/cli/src/commands/hive-mind.ts:1210-1221`) doesn't even expose a `--strategy` flag. Net effect: `claude-flow hive-mind init -c byzantine` (the docs' own example) followed by `consensus -a propose` always resolves via plain-majority Raft, never Byzantine fault detection — and `gossip`/`crdt` are accepted as init-time labels with **no corresponding branch anywhere** in the resolution code. Fully reachable in production, not gated behind an unused package. Not implemented tonight (out of surface — a `hive-mind` or `swarm` DEEP night candidate). Files: `hive-mind-tools.ts:22,43,326,551,621-622`; `hive-mind.ts:1210-1221`.
